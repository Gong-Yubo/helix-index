## 2. 数据来源与装配

- **采样**：候选池排序用 `xxh64(qid, SEED_QID)` 取前 2000；负例用 `xxh64(pid, SEED_NEG)` 哈希秩 + 7K 容量最小堆精确取秩（非 Bernoulli，防 rank 漂移）。
- **过滤**：仅保留 grade≥2 存在且 query 长度 4~40 字符的 query。
- **装配结果**：320 query / 12,000 段落；分级标注 `[grade1=9867, grade2=817, grade3=1042, grade4=274]`；qrels pid **32562/32562 全命中**。
- **分桶**（每桶 80 条）：`mixed`（含 ASCII）/ `natural`（≥16 字符无 ASCII）/ `exact`（o* 词汇重合度 ≥0.5）/ `paraphrase`（o* <0.5）。o* 直方图主峰在 0.9~1.0，0.5 阈值区分度成立，维持 0.5 定稿。
- **单 chunk 路径**：段落→chunk 断言不成立（4638/12000 多 chunk），按设计预案（5.2 步骤 8）改走「每段落强制单 chunk」（`Chunker::new(200_000, 0)`），消除同一 passage 多 chunk 双计风险。

## 4. tantivy 基线对照（ADR-007 gate）

- 自研 BM25 NDCG@10 = **0.4429** vs tantivy 0.26 NDCG@10 = **0.4415**，相对差 **0.31%**（阈值 5%）。

## 5. BM25 网格搜索与参数定稿

16 格（k1 ∈ {1, 1.2, 1.5, 2} × b ∈ {0.3, 0.5, 0.75, 0.9}），NDCG@10 宏平均：

| k1 \ b | 0.3 | 0.5 | 0.75 | 0.9 |
| --- | --- | --- | --- | --- |
| 1.0 | 0.4232 | 0.4361 | 0.4397 | 0.4382 |
| 1.2 | 0.4252 | 0.4388 | 0.4429 | 0.4416 |

  低于 run-to-run 噪声量级（≈0.002）；参数提升属"微调"而非结构性收益，不作过度解读。

### 8.2 NFR-03 索引构建

`helix build --vectors`（release），embed 单独计时：

| 口径 | chunk 数 | 纯索引构建 | embed | 含落盘总耗时 | 目标 |
| --- | --- | --- | --- | --- | --- |
| 单 chunk（`--single-chunk`，对齐 NFR-01 的"1 万 chunk"） | 12,000 | ~3s | 233.7s | **236.7s** | < 120s ✗ |
| 默认 Chunker（512/64） | 24,378 | 1.97s | ~530s | **532.3s** | < 120s ✗ |

> **P6 重测（2026-09-04）**：门面层写缓冲 + 批量 embed 后，embed 209.9s、总 225.5s
> （单 chunk 12K），比 P5 略快但**仍未达标**。`batch_size` 实测 32/64/128/256 吞吐
> 62.6/59.1/54.4/51.6 条/s——差异 <20% 且小 batch 略快，说明瓶颈是 ort 推理本身
> 而非 batch 规模。原「embed 耗时」在 commit 处计时只测到最后一批（581ms）是
> 口径 bug，已改为 `SearchIndex::embed_elapsed()` 累计值（见 CHANGELOG P6）。

- **根因**：ort CPU 推理吞吐 ~51 条/秒（19.5ms/条），远低于 P0 单条 1.58ms 的直觉外推。
  embed 12000 条与 24378 条均呈线性（非超线性），瓶颈是本地 CPU 推理本身。
- **缓解路径（P7）**：① 分块 + 多进程并行 embed；② GPU/加速推理后端；
  ③ 更小/量化模型（fastembed 支持 Q 后缀静态量化）；④ 增量构建（只 embed 新增文档）。
  当前 12K 段落 ~226s 的绝对耗时对"一次性冷建库"可接受，但不满足 <120s 目标。

### 8.3 NFR-04 冷启动

| 口径 | P5 实测（图不持久化） | V2 Step 2 实测（图持久化后） | 目标 |
| --- | --- | --- | --- |
| 快照加载（`storage::load`，含位图/字段索引重建） | 53.4ms（12K）/ 106.7ms（24K） | **57~77ms**（12K，3 次） | < 2s ✅ |
| HNSW 图加载（sidecar 快路径） | ——（无此路径） | **23~37ms**（12K，3 次） | —— |
| **完整冷启动（上两项之和）** | **≈ 11.6s** ❌ | **≈ 100ms**（82~100ms） ✅ | **< 2s** |
| 降级路径：图重建（图 sidecar 缺失/损坏） | 11.57s（12,000 条） | **≈10~11.5s**（12,000 条） | 仅降级时出现 |
| 图 sidecar dump 耗时 | —— | 43.5ms（31.6MB） | —— |

**V2 Step 2 已解决 D7**（2026-09-06，ADR-A 方案 C）：图 sidecar 三件套
（`foo.idx.hnsw.{graph,data,manifest}`）+ manifest 作唯一原子发布点。
完整冷启动从 **11.6s 降到 ≈100ms**（约 **116×**），NFR-04 达标且余量 20×。

> ⚠️ **关于数字的可复现性**：本节的耗时均为**单次诚实记录**，跨运行有波动
> （快照加载 57~77ms、图加载 23~37ms、图重建 9.96~11.61s），
> graph 体积也随 HNSW 拓扑在 7.9~8.1MB 间浮动（与 R-P5-13 同源）。
> 因此除「完整冷启动 < 2s」这个**有 20× 余量的判定**外，其余一律给范围。
> 评审独立复现时快照加载到 0.06ms 精度吻合，属同机同流程的诚实记录。

**体积代价（`file_dump` 只支持 `DumpMode::Full`，向量必然被复制一份）**：

| 项 | 大小 |
| --- | --- |
| 快照 `foo.idx` | 52.3 MB |
| 图 `foo.idx.hnsw.graph` | 7.9~8.1 MB（随拓扑小幅波动） |
| 数据 `foo.idx.hnsw.data` | 23.7 MB |
| manifest | 91 B |
| **合计（磁盘增量）** | **≈84 MB（1.6×）** |

⚠️ **达标依赖图 sidecar 命中**：降级路径仍是 ~11s（快照 56~78ms + 图重建 ≈10~11.5s）。
单次实测有 ±15% 波动（三次 9.96 / 11.01 / 10.73s），故此处给范围而非精确值。
故 NFR-07 扩口径为「**降级不得静默**」——`GraphStatus::Rebuilt(reason)` 必须显式可见，
否则冷启动会静默退化到 10s 而不自知。`--no-graph-persist` 是磁盘紧张时的逃生舱。
R-P5-13（跨进程图抖动）一并消解：图落盘即冻结拓扑，**同一快照两次加载逐位一致**——
注意口径是「两次**加载**」而非「两次**建库**」（后者在 `parallel_insert` 下不成立）。

### 8.6 并行建图（`parallel_build`，D-S2-05 的决策数据）

> 复现：`cargo run -p helix-core --release --example bench_parallel_build -- [n] [dim] [repeats] [real]`
> （第 4 参 `real` 用 T2Ranking 真实语料 + `LocalEmbedder`；否则用合成随机向量）

| 规模 / 语料 | 串行建图 | 并行建图 | **加速比** | oracle Top-10 重合率（串 / 并） |
| --- | --- | --- | --- | --- |
| 12K 合成随机向量（dim=512） | 19.229s | 3.634s | **5.29×** | 0.990 / 0.990 |
| 50K 合成随机向量（dim=512） | 171.837s | 32.655s | **5.26×** | 0.935 / 0.905 |
| **12K 真实语料**（T2Ranking + LocalEmbedder） | **11.676s** | **2.182s** | **5.35×** | **0.995 / 0.995** |

（每档 2~3 轮取中位数；`parallel_inserts()` = 1，确认**真的走了并行**分支）

**结论**：

1. **加速比稳定在 ≈5.3×，且与规模无关**（12K 与 50K 一致），远高于评审时的悲观预期（2~3×）。
2. **质量代价可忽略**：真实语料上 oracle 重合率**无差异**（0.995 / 0.995）；
   合成随机向量（512 维几乎两两等距的**对抗性输入**）在 50K 时低约 3pp —— 这是最坏情况，
   生产语料有聚类结构，不会退化到这个水平。
3. **对 NFR-03 的意义有限**：12K 构建 225.5s 里 embed 占 215.8s，建图仅 11.7s ⇒
   并行后省约 9.5s（≈4%），**不足以让 NFR-03（<120s）达标**——瓶颈是 ort 推理（issue #2）。
   但建图本身不再是构建期的显著项。
4. ⇒ **建议把 `parallel_build` 默认值从「关」翻为「开」**：5.3× 加速、质量无损，
   且 NFR-06 不受影响（图落盘即冻结拓扑，验收口径是「同快照两次**加载**」）。
   唯一代价「同批向量两次建库结果不同」已被 NFR-06 显式排除。
   ⚠️ **翻转需独立 PR**：`S2-T22` 当前断言「默认必须串行（保确定性）」，
   翻默认值必须同步改这条护栏的语义，不能顺手夹带。

⚠️ **口径差异（别横比绝对耗时）**：本基准用 `HnswRsIndex::with_capacity` 默认参数 +
**单次全量 `add_batch`**；而 §8.2 的「纯索引构建 ~3s」走门面层分批 add（`batch_size=64`）。
两条路径的参数与批次不同，**绝对耗时不可直接横比；只有同口径下的加速比（5.3×）是可信结论**。

### 8.7 原子快照的 fsync 代价（V2 Step 3 / D-S3-06 / S3-08）

> 复现：`cargo run -p helix-core --release --example bench_save_fsync -- [n] [dim] [repeats]`
> 口径：12K T2Ranking 真实语料正文（BM25）+ 合成 512 维向量（快照 **54,476,915 字节
> ≈ 54.5MB**，52MB 级；fsync 代价只取决于字节数，向量用合成避免一次性 ~220s embed）。
> 每档 3 轮取 min~max（单次波动可达 ±15%）；两版产物的 CRC 完全一致
> （`0x576e065f`）——**格式零变化**得到字节级实测印证。

| 版本 | save 耗时（3 轮 min~max） | 写协议 |
| --- | --- | --- |
| 改造前（main @ `2a18fdc`） | **0.034 ~ 0.040s** | `File::create` 直写 + flush（无原子性） |
| 改造后（V2 Step 3） | **0.067 ~ 0.075s** | tmp + flush + `sync_all` + rename + fsync 父目录 |

**结论**：

1. **fsync 绝对代价 ≈ +0.027~0.035s**（约 1.7~2.1×，本机 NVMe SSD）：两次 `sync_all`
   （54.5MB 文件 + 父目录）合计约 30ms，低于设计预估的 50~300ms 下限。
   ⚠️ **平台口径**（评审 #27-3 核实）：目录 fsync 是 best-effort——实测机
   （macOS/APFS，rustc 1.90）上目录 fd `sync_all` **实测成功**，本表增量含真实
   目录 fsync；Windows（打不开目录）及部分文件系统上会静默跳过，届时增量
   基本只来自 54.5MB 文件那一次 `sync_all`，结论量级不变。
2. **不触碰任何 NFR**（D-S3-06 的验收前提）：save 是用户显式调用的低频操作，
   NFR-02 查询 / NFR-03 构建 / NFR-04 冷启动均不含 save；54MB 级 save 全程 <0.1s。
3. HDD / 网络卷上代价会显著放大（§9 风险接受项），但语义不变：真源不提供跳过 fsync 的逃生舱。

### 8.8 churn（零散写入）workload——墓碑回收实测（V2 Step 4 / S4-09）

> 复现：`./scripts/eval_churn.sh`（默认 10K × churn {0.1, 0.3} × 5 轮）。
> 口径：`crates/core/examples/churn_bench`——10K 合成 corpus（`synth-10000`，正文真实文本）
> + **内置确定性 SynthEmbedder**（LCG，dim=512，L2 归一化，id=`synth-512`，§4.8 / D-S4-06）。

⚠️ **方法与噪声（判读前必读）**：

- **两轮非交错执行**（先全 `off`、后全强制精确），控制组 `none` 档两轮同走 ANN，
  却在第二轮整体偏慢 **×1.382(vector) / ×1.541(hybrid)**（**`mean_vector_ms` 口径**；
  若按表 1 的 P99 复算则为 ×1.61 / ×1.70，勿混用）⇒ **跨轮比较须按控制组归一**。
- **P99 在同轮内也不稳**：`sel-10%`(10000) 与 `tenant-10%`(9946) 的精确 P99 是
  8.46 vs 11.77ms，而两者**工作量几乎相同**（±40% 抖动）⇒ **决策改看 `mean_vector_ms`**
  （1000 个 `Metrics` 样本的均值，比百分位稳）。
- 归一后加速（`mean_vector_ms`，ANN × 控制组因子）：`46.6× / 11.2× / 50.7× / 2.06× / 1.03× / 0.96× / 1.43×`。
- **交叉点「≈ 9700」是插值、不是实测**：按**归一后**加速（`tier-5%` 2.06× / `tenant-10%` 0.96×）
  线性插值 = 9768（不同插值方式下 9.6K~9.9K）；若按**未归一**原始值插值则 ≈7.2K~8.1K——
  插值对两轮漂移敏感（`tenant-10%` 归一后 ANN 优势仅 4%）。⇒ **实测事实只有两端点的胜负符号**
  （不归一也成立），插值仅用于在区间内选档；8192 的稳妥性锚在「低于首个实测反转档位 9946」
  与 R31 的规模论证（交叉点随规模下移 ⇒ 宁低勿高），**不锚在插值精度上**。

**结论**：

1. **阈值定稿 `8192`**（原初值 1024）。判据是**不需要归一化就成立的两个端点**：
   `allowed=5043` 精确明确胜（6.93 → 4.64ms），`allowed=9946` ANN 明确胜（4.62 → 6.64ms）
   ⇒ 交叉点落在 `(5043, 9946)`，插值 ≈ **9700**（口径见上方第 4 条）；取 2¹³——低于归一插值
   ~15%、更低于首个实测反转档位 9946（R31：`O(N)` 项随规模增长 ⇒ 交叉点**下移**）。
   **原初值 1024 过保守**——会漏掉 `tier-5%`(5043) 这个实测 2.06× 的档位。
2. **NFR-13 预算定双口径**：
   - **常规档位（字段索引命中）≤ 20ms** —— 实测最差 **7.06ms**（`sel-0.1%` hybrid），余量 **2.8×**
     ⇒ **原拟的 20ms 被证实**；
   - **降级字段档位 ≤ 35ms** —— 实测最差 **22.84ms**（`ts-range-degraded` hybrid），
     其中**过滤求值自身 8.77ms**（D-S5-09 已接受、与向量路正交），向量路仅 3.15ms。
     单值口径须 ≥ 35ms 才不被这个**与向量路无关**的成本顶穿 ⇒ 拆口径才能既真实又有鉴别力。
3. **方案 A 达标 ⇒ 不做方案 B**（Q5 结案）。

#### 8.10.1 测量协议（⚠️ 三处与设计 §4.2.5 / §4.2.1 不同，均为实现期替换）

| # | 设计原写 | 实际协议 | 原因 |
| --- | --- | --- | --- |
| 1 | **一次进程内**跑完所有档位 | **逐档位独立进程 + 按波交错**（A/B/C 各起一个进程算一波，跑 3 波） | 单 session 在 batch 64 × 长文本下峰值 RSS 就 **2~3.3 GB**（**激活张量**，不是权重）；7 个 session（`1+2+4`）并存会顶穿本机 32 GB ⇒ 换页会**均匀拖慢所有档位**，档位间比较失去意义 |
| 2 | **档位内两轮、顺序交错（A/B/A/B）** | **每档位每波只有一个计时样本**（交错只在「波」这一层）⇒ **每档位样本量 = 3** | 与 1 同源：内存隔离要求"一档位一进程" |
| 3 | 每档位 **1 轮完整语料预热、丢弃计时** | 预热轮跑在**一次性进程**里（只暖 OS 文件缓存）；**每个计时波都是它自己那个进程的首次推理**（计时波恒传 `--warmup 0`） | 脚本要隔离内存，就无法把预热"带进"被计时进程；`run_pass` 的秒表起在 `SessionPool::build` **之后**，故模型加载与 ONNX 图优化本就不进计时 |

#### 8.10.4 表 3 · 峰值 RSS 的归因：固定文本长度、只变语料规模（评审 F5，新增）

先前那张「真实 CLI 旁证表」同时变了**文本长度**与**批次数**两个变量 ⇒ 只能证明相关。本表固定语料
（全部取 `t2-corpus.jsonl` 前 N 段，长度分布同一总体），**只变 N**：

| N（段） | 批次数（÷64） | 耗时 | 峰值 RSS（首次 / 复跑） |
| --- | --- | --- | --- |
| 64 | 1 | 1.10s | **2.11 / 2.11 GB** |
| 512 | 8 | 8.86s | **3.31 / 3.31 GB** |
| 4096 | 64 | 69.24s | **3.33 / 3.33 GB** |

⇒ **峰值 RSS 在第一个 batch 就到 2.11 GB，8 个 batch 后饱和于 3.3 GB，语料再放大 8 倍不再变**。
⇒ 结论：**由 `batch × 序列长度`（单批激活）决定，与语料规模解耦**（复跑逐位一致 2.11 / 3.31 / 3.33）。
这同时回答了评审的「batch 固定 64、语料涨到 4000 段为什么从 2.32 GB 涨到 3.33 GB」：
那是 **1 个 batch vs 63 个 batch** 的差别，不是语料总量的线性效应。

#### 8.10.6 结论（Q1 / Q2 结案；D-S6-01 判「不投」）

**T7-09 判「不投」——本 Step 只交付 spike 与数据，不落地 M 级改造。**

1. **E2 为何是微弱收益**（与设计 §2.3 的预判一致）：`intra_threads` 默认 `None` **已用满全部核**；
   E2 只是把 10 个核**切开重新分配**（2×5 / 4×3），总计算量不变 ⇒ 换来 +11.7%~+16.0% 的调度改善，
   代价是 **RSS 近线性翻倍**（R36 命中）。这正是设计 §4.3 预列三种结果中的**第 2 种（零收益）**。
2. **E3 的真实障碍是"动态形状"**：`RequireStaticInputShapes` 默认关时，CoreML 会因每个 batch 形状不同
   反复重编译 ⇒ 128 段就要 114.6s；打开静态形状 + `MLProgram` 后回到与 CPU 持平。
   ⚠️ **但持平仍是"不投"**：门槛是 ≥ +30%，且 EP 还有向量数值变更（§3.5）+ 快照语义变更（§3.1）两条不为零的代价。
3. **对 NFR-03 ① / NFR-05 的影响**：本次**不改动任何默认路径** ⇒ ① 仍为 225.5s、峰值口径不变；
   本 Step 对 ① 的承诺只是"别弄坏"，**已满足**。
4. **S6-04（池化）/ S6-05（EP 接入）据此不开工**；`coreml` feature 按**评审裁定 2** 作为
   **默认关闭的探针基础设施**保留（它是结论的物证 + 换机重测的唯一入口；
   Cargo.toml 已注明「不在 CI 覆盖内、预期会随 ort 升级腐化」）。
5. **Q8 最新状态**：见 8.10.7。

#### 8.10.7 Q8（新增待决）：build 路径 RSS 是否纳入 NFR-05 / 立 R41

- **事实**：NFR-05 的 372 MB 是 `search` 路径（batch 1）口径；build 路径实测 **2.3~3.33 GB**（表 3）。
- **本次补的证据**（按**评审裁定 3** 的第一步）：表 3 三点 ⇒ RSS **与语料规模解耦**、1 batch 后饱和
  ⇒ **R41 的预算形态应按 `batch × 序列长度` 给，而不是按语料规模给**。
- **未做**（按裁定 3 的第二步）：**不把 build 路径并进 NFR-05 的既有读数**、**本 PR 不擅自登记 R41** ——
  登记会牵动定义面四处 + 版本行，归 **S6-10**。**待评审裁定。**

#### 8.10.8 局限（如实记录）

- **机器单一**（Apple M5 / 10 核 / 32 GB / macOS 26）⇒ **结论不外推**；换机器（尤其 x86 或旧款 Apple Silicon）须重跑。
- **E2 只测了一种切法**（`ceil(核数 / sessions)`）⇒ 结论的准确表述是「**这个形态**不投」，**不是**「池化一律无收益」；
  且 **×2 / ×4 只在 4000 段长文本下测过**。（评审另跑 256 段小语料时 e2-2 为 **−22%**，与"零收益"同向。）
- **E3 只测到 512 段**（默认档病态到 128 段就要 114.6s）；**未测**「多 session × CoreML」组合；
  且「慢源于动态形状」是**推断而非观测**（见 8.10.3）。
- **热量累积未被排查**：`--coreml-static-shapes` 默认档 128 段就 17 GB，像有内存累积 ⇒ **未做专项排查**。
- **跨时段数字不可相减**：本次复跑 e1（同进程、`warmup 1`）中位 **69.43s**，而表 1 的 e1（独立进程、`warmup 0`）是 **63.05s**
  —— 差 +10.1%，但两次测量**相隔数小时**，**该差不可归因**（时段/热状态漂移）。⇒ 恰好说明评审新增 H 的立场：
  **跨协议、跨时段的数字不能互相解释**（`perf-ab-calibration` 纪律）。
- **冷/热进程差异未做匹配条件的 A/B**：评审新增 I 的 71.01s（预热轮）vs 63.05s（计时波）**含 process 启动与冷 page cache**，
  **不能当成纯"预热收益"**；本次按评审给的第二条修法处理（改写协议描述），未改 `--warmup` 传参。
- **e2-4 的 +16.0% 与自身噪声不可分**（带宽 16.3%，见 8.10.2）。

#### 8.10.9 数值口径注记（评审新增 G）

- **控制组带宽 0.9%**（`(max−min)/min = (63.18−62.61)/62.61 = 0.91%`）——先前写 1.0% 是舍入过头。
- **单 session 峰值 RSS 统一写 3.33 GB**（e1 实测）。先前 CHANGELOG / 脚本注释里的「约 2 GB」指**单批激活**
  （表 3 的 N=64 点 = 2.11 GB），两者**不是同一个量**，已分别标明。
- **e2-4 峰值 12.96 GB**（脚本注释里的「13 GB」是舍入）。
- **吞吐列口径**：本表用 **语料规模 / 中位耗时**；脚本摘要另打印「各波吞吐的中位数」⇒ e2-2 两处为 70.8 / 70.9，
  差异来自两条路径，**表以"中位耗时"那条为准**（已写进脚本表头）。

## 9. 数据诚信声明

**已知偏差**：
1. **随机负例的潜在假负例**：负例按哈希秩均匀抽样，未标注的段落可能含相关段落（假负例）。
2. **分桶为启发式代理**：o* 词汇重合度不是人工判类，exact/paraphrase 边界存在误分。
3. **人类搜索 query 作为 Agent query 的代理**：T2Ranking 是网络搜索日志，非 LLM 生成 query（query 分布、噪声形态与 Agent 场景有差异，见项目立论五差异）。
4. **12K 子集难度低于 230 万全库**：BM25 MRR@10=0.6394（子集）vs 论文全库 0.359，绝对指标不可与论文基线直接对比，仅量级对照。

**结论适用范围**：结论仅对「T2Ranking 中文网络语料 + bge-small-zh-v1.5 + 12K 段落」成立，
不外推到其他域、规模或查询分布。

**未达预期项的如实记录**：
- **hybrid NDCG 未超越 vector 单路**（0.5183 vs 0.5249，p=0.385 不显著）：RRF 融合在
  paraphrase 桶被弱路 BM25 稀释（3.3 节）。但 hybrid 在 MRR@10(1) 与 Recall@10(1) 两项
  对 Agent 场景更关键的指标上全场最高，且 exact/natural/mixed 桶显著优于 BM25 单路。
  融合的价值在「首条精确率」而非「NDCG 整体」——这与项目质量属性优先级（MRR > Recall > NDCG）一致。
- **预期占优假设（9.4）在 exact 桶被推翻**：exact 桶 hybrid 最优而非 BM25（3.3 节）。
- ~~**NFR-04 冷启动未达标**：HNSW 图重建 11.57s > 2s 目标（P4 已知风险 D7）~~ → **已解决**（2026-09-06，V2 Step 2 / ADR-A）：完整冷启动 ≈100ms，达标。代价是磁盘 1.6×，且达标依赖图 sidecar 命中（降级路径仍 ~10s，故配 NFR-07 降级可观测）。
