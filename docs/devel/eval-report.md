## 2. 数据来源与装配

- **采样**：候选池排序用 `xxh64(qid, SEED_QID)` 取前 2000；负例用 `xxh64(pid, SEED_NEG)` 哈希秩 + 7K 容量最小堆精确取秩（非 Bernoulli，防 rank 漂移）。
- **过滤**：仅保留 grade≥2 存在且 query 长度 4~40 字符的 query。
- **装配结果**：320 query / 12,000 段落；分级标注 `[grade1=9867, grade2=817, grade3=1042, grade4=274]`；qrels pid **32562/32562 全命中**。
- **分桶**（每桶 80 条）：`mixed`（含 ASCII）/ `natural`（≥16 字符无 ASCII）/ `exact`（o* 词汇重合度 ≥0.5）/ `paraphrase`（o* <0.5）。o* 直方图主峰在 0.9~1.0，0.5 阈值区分度成立，维持 0.5 定稿。
- **单 chunk 路径**：段落→chunk 断言不成立（4638/12000 多 chunk），按设计预案（5.2 步骤 8）改走「每段落强制单 chunk」（`Chunker::new(200_000, 0)`），消除同一 passage 多 chunk 双计风险。

## 4. tantivy 基线对照（ADR-007 gate）

- 自研 BM25 NDCG@10 = **0.4429** vs tantivy 0.26 NDCG@10 = **0.4415**，相对差 **0.31%**（阈值 5%）。

## 5. BM25 网格搜索与参数定稿

16 格（k1 ∈ {1, 1.2, 1.5, 2} × b ∈ {0.3, 0.5, 0.75, 0.9}），NDCG@10 宏平均：

| k1 \ b | 0.3 | 0.5 | 0.75 | 0.9 |
| --- | --- | --- | --- | --- |

### 8.2 NFR-03 索引构建

`helix build --vectors`（release），embed 单独计时：

| 口径 | chunk 数 | 纯索引构建 | embed | 含落盘总耗时 | 目标 |
| --- | --- | --- | --- | --- | --- |
| 单 chunk（`--single-chunk`，对齐 NFR-01 的"1 万 chunk"） | 12,000 | ~3s | 233.7s | **236.7s** | < 120s ✗ |
| 默认 Chunker（512/64） | 24,378 | 1.97s | ~530s | **532.3s** | < 120s ✗ |

> **P6 重测（2026-09-04）**：门面层写缓冲 + 批量 embed 后，embed 209.9s、总 225.5s
> （单 chunk 12K），比 P5 略快但**仍未达标**。`batch_size` 实测 32/64/128/256 吞吐
> 62.6/59.1/54.4/51.6 条/s——差异 <20% 且小 batch 略快，说明瓶颈是 ort 推理本身
> 而非 batch 规模。原「embed 耗时」在 commit 处计时只测到最后一批（581ms）是
> 口径 bug，已改为 `SearchIndex::embed_elapsed()` 累计值（见 CHANGELOG P6）。

- **根因**：ort CPU 推理吞吐 ~51 条/秒（19.5ms/条），远低于 P0 单条 1.58ms 的直觉外推。
  embed 12000 条与 24378 条均呈线性（非超线性），瓶颈是本地 CPU 推理本身。
- **缓解路径（P7）**：① 分块 + 多进程并行 embed；② GPU/加速推理后端；
  ③ 更小/量化模型（fastembed 支持 Q 后缀静态量化）；④ 增量构建（只 embed 新增文档）。
  当前 12K 段落 ~226s 的绝对耗时对"一次性冷建库"可接受，但不满足 <120s 目标。

### 8.3 NFR-04 冷启动

| 口径 | P5 实测（图不持久化） | V2 Step 2 实测（图持久化后） | 目标 |
| --- | --- | --- | --- |
| 快照加载（`storage::load`，含位图/字段索引重建） | 53.4ms（12K）/ 106.7ms（24K） | **57~77ms**（12K，3 次） | < 2s ✅ |
| HNSW 图加载（sidecar 快路径） | ——（无此路径） | **23~37ms**（12K，3 次） | —— |
| **完整冷启动（上两项之和）** | **≈ 11.6s** ❌ | **≈ 100ms**（82~100ms） ✅ | **< 2s** |
| 降级路径：图重建（图 sidecar 缺失/损坏） | 11.57s（12,000 条） | **≈10~11.5s**（12,000 条） | 仅降级时出现 |
| 图 sidecar dump 耗时 | —— | 43.5ms（31.6MB） | —— |

**V2 Step 2 已解决 D7**（2026-09-06，ADR-A 方案 C）：图 sidecar 三件套
（`foo.idx.hnsw.{graph,data,manifest}`）+ manifest 作唯一原子发布点。
完整冷启动从 **11.6s 降到 ≈100ms**（约 **116×**），NFR-04 达标且余量 20×。

> ⚠️ **关于数字的可复现性**：本节的耗时均为**单次诚实记录**，跨运行有波动
> （快照加载 57~77ms、图加载 23~37ms、图重建 9.96~11.61s），
> graph 体积也随 HNSW 拓扑在 7.9~8.1MB 间浮动（与 R-P5-13 同源）。
> 因此除「完整冷启动 < 2s」这个**有 20× 余量的判定**外，其余一律给范围。
> 评审独立复现时快照加载到 0.06ms 精度吻合，属同机同流程的诚实记录。

**体积代价（`file_dump` 只支持 `DumpMode::Full`，向量必然被复制一份）**：

| 项 | 大小 |
| --- | --- |
| 快照 `foo.idx` | 52.3 MB |
| 图 `foo.idx.hnsw.graph` | 7.9~8.1 MB（随拓扑小幅波动） |
| 数据 `foo.idx.hnsw.data` | 23.7 MB |
| manifest | 91 B |
| **合计（磁盘增量）** | **≈84 MB（1.6×）** |

⚠️ **达标依赖图 sidecar 命中**：降级路径仍是 ~11s（快照 56~78ms + 图重建 ≈10~11.5s）。
单次实测有 ±15% 波动（三次 9.96 / 11.01 / 10.73s），故此处给范围而非精确值。
故 NFR-07 扩口径为「**降级不得静默**」——`GraphStatus::Rebuilt(reason)` 必须显式可见，
否则冷启动会静默退化到 10s 而不自知。`--no-graph-persist` 是磁盘紧张时的逃生舱。
R-P5-13（跨进程图抖动）一并消解：图落盘即冻结拓扑，**同一快照两次加载逐位一致**——
注意口径是「两次**加载**」而非「两次**建库**」（后者在 `parallel_insert` 下不成立）。

### 8.6 并行建图（`parallel_build`，D-S2-05 的决策数据）

> 复现：`cargo run -p helix-core --release --example bench_parallel_build -- [n] [dim] [repeats] [real]`
> （第 4 参 `real` 用 T2Ranking 真实语料 + `LocalEmbedder`；否则用合成随机向量）

| 规模 / 语料 | 串行建图 | 并行建图 | **加速比** | oracle Top-10 重合率（串 / 并） |
| --- | --- | --- | --- | --- |
| 12K 合成随机向量（dim=512） | 19.229s | 3.634s | **5.29×** | 0.990 / 0.990 |
| 50K 合成随机向量（dim=512） | 171.837s | 32.655s | **5.26×** | 0.935 / 0.905 |
| **12K 真实语料**（T2Ranking + LocalEmbedder） | **11.676s** | **2.182s** | **5.35×** | **0.995 / 0.995** |

（每档 2~3 轮取中位数；`parallel_inserts()` = 1，确认**真的走了并行**分支）

**结论**：

1. **加速比稳定在 ≈5.3×，且与规模无关**（12K 与 50K 一致），远高于评审时的悲观预期（2~3×）。
2. **质量代价可忽略**：真实语料上 oracle 重合率**无差异**（0.995 / 0.995）；
   合成随机向量（512 维几乎两两等距的**对抗性输入**）在 50K 时低约 3pp —— 这是最坏情况，
   生产语料有聚类结构，不会退化到这个水平。
3. **对 NFR-03 的意义有限**：12K 构建 225.5s 里 embed 占 215.8s，建图仅 11.7s ⇒
   并行后省约 9.5s（≈4%），**不足以让 NFR-03（<120s）达标**——瓶颈是 ort 推理（issue #2）。
   但建图本身不再是构建期的显著项。
4. ⇒ **建议把 `parallel_build` 默认值从「关」翻为「开」**：5.3× 加速、质量无损，
   且 NFR-06 不受影响（图落盘即冻结拓扑，验收口径是「同快照两次**加载**」）。
   唯一代价「同批向量两次建库结果不同」已被 NFR-06 显式排除。
   ⚠️ **翻转需独立 PR**：`S2-T22` 当前断言「默认必须串行（保确定性）」，
   翻默认值必须同步改这条护栏的语义，不能顺手夹带。

⚠️ **口径差异（别横比绝对耗时）**：本基准用 `HnswRsIndex::with_capacity` 默认参数 +
**单次全量 `add_batch`**；而 §8.2 的「纯索引构建 ~3s」走门面层分批 add（`batch_size=64`）。
两条路径的参数与批次不同，**绝对耗时不可直接横比；只有同口径下的加速比（5.3×）是可信结论**。

### 8.7 原子快照的 fsync 代价（V2 Step 3 / D-S3-06 / S3-08）

> 复现：`cargo run -p helix-core --release --example bench_save_fsync -- [n] [dim] [repeats]`
> 口径：12K T2Ranking 真实语料正文（BM25）+ 合成 512 维向量（快照 **54,476,915 字节
> ≈ 54.5MB**，52MB 级；fsync 代价只取决于字节数，向量用合成避免一次性 ~220s embed）。
> 每档 3 轮取 min~max（单次波动可达 ±15%）；两版产物的 CRC 完全一致
> （`0x576e065f`）——**格式零变化**得到字节级实测印证。

| 版本 | save 耗时（3 轮 min~max） | 写协议 |
| --- | --- | --- |
| 改造前（main @ `2a18fdc`） | **0.034 ~ 0.040s** | `File::create` 直写 + flush（无原子性） |
| 改造后（V2 Step 3） | **0.067 ~ 0.075s** | tmp + flush + `sync_all` + rename + fsync 父目录 |

**结论**：

1. **fsync 绝对代价 ≈ +0.027~0.035s**（约 1.7~2.1×，本机 NVMe SSD）：两次 `sync_all`
   （54.5MB 文件 + 父目录）合计约 30ms，低于设计预估的 50~300ms 下限。
   ⚠️ **平台口径**（评审 #27-3 核实）：目录 fsync 是 best-effort——实测机
   （macOS/APFS，rustc 1.90）上目录 fd `sync_all` **实测成功**，本表增量含真实
   目录 fsync；Windows（打不开目录）及部分文件系统上会静默跳过，届时增量
   基本只来自 54.5MB 文件那一次 `sync_all`，结论量级不变。
2. **不触碰任何 NFR**（D-S3-06 的验收前提）：save 是用户显式调用的低频操作，
   NFR-02 查询 / NFR-03 构建 / NFR-04 冷启动均不含 save；54MB 级 save 全程 <0.1s。
3. HDD / 网络卷上代价会显著放大（§9 风险接受项），但语义不变：真源不提供跳过 fsync 的逃生舱。

### 8.8 churn（零散写入）workload——墓碑回收实测（V2 Step 4 / S4-09）

> 复现：`./scripts/eval_churn.sh`（默认 10K × churn {0.1, 0.3} × 5 轮）。
> 口径：`crates/core/examples/churn_bench`——10K 合成 corpus（`synth-10000`，正文真实文本）
> + **内置确定性 SynthEmbedder**（LCG，dim=512，L2 归一化，id=`synth-512`，§4.8 / D-S4-06）。

- **两轮非交错执行**（先全 `off`、后全强制精确），控制组 `none` 档两轮同走 ANN，
  却在第二轮整体偏慢 **×1.382(vector) / ×1.541(hybrid)**（**`mean_vector_ms` 口径**；
  若按表 1 的 P99 复算则为 ×1.61 / ×1.70，勿混用）⇒ **跨轮比较须按控制组归一**。
- **P99 在同轮内也不稳**：`sel-10%`(10000) 与 `tenant-10%`(9946) 的精确 P99 是
  8.46 vs 11.77ms，而两者**工作量几乎相同**（±40% 抖动）⇒ **决策改看 `mean_vector_ms`**
  （1000 个 `Metrics` 样本的均值，比百分位稳）。
- 归一后加速（`mean_vector_ms`，ANN × 控制组因子）：`46.6× / 11.2× / 50.7× / 2.06× / 1.03× / 0.96× / 1.43×`。
- **交叉点「≈ 9700」是插值、不是实测**：按**归一后**加速（`tier-5%` 2.06× / `tenant-10%` 0.96×）
  线性插值 = 9768（不同插值方式下 9.6K~9.9K）；若按**未归一**原始值插值则 ≈7.2K~8.1K——
  插值对两轮漂移敏感（`tenant-10%` 归一后 ANN 优势仅 4%）。⇒ **实测事实只有两端点的胜负符号**
  （不归一也成立），插值仅用于在区间内选档；8192 的稳妥性锚在「低于首个实测反转档位 9946」
  与 R31 的规模论证（交叉点随规模下移 ⇒ 宁低勿高），**不锚在插值精度上**。

**结论**：

1. **阈值定稿 `8192`**（原初值 1024）。判据是**不需要归一化就成立的两个端点**：
   `allowed=5043` 精确明确胜（6.93 → 4.64ms），`allowed=9946` ANN 明确胜（4.62 → 6.64ms）
   ⇒ 交叉点落在 `(5043, 9946)`，插值 ≈ **9700**（口径见上方第 4 条）；取 2¹³——低于归一插值
   ~15%、更低于首个实测反转档位 9946（R31：`O(N)` 项随规模增长 ⇒ 交叉点**下移**）。
   **原初值 1024 过保守**——会漏掉 `tier-5%`(5043) 这个实测 2.06× 的档位。
2. **NFR-13 预算定双口径**：
   - **常规档位（字段索引命中）≤ 20ms** —— 实测最差 **7.06ms**（`sel-0.1%` hybrid），余量 **2.8×**
     ⇒ **原拟的 20ms 被证实**；
   - **降级字段档位 ≤ 35ms** —— 实测最差 **22.84ms**（`ts-range-degraded` hybrid），
     其中**过滤求值自身 8.77ms**（D-S5-09 已接受、与向量路正交），向量路仅 3.15ms。
     单值口径须 ≥ 35ms 才不被这个**与向量路无关**的成本顶穿 ⇒ 拆口径才能既真实又有鉴别力。
3. **方案 A 达标 ⇒ 不做方案 B**（Q5 结案）。

| # | 设计原写 | 实际协议 | 原因 |
| --- | --- | --- | --- |
| 1 | **一次进程内**跑完所有档位 | **逐档位独立进程 + 按波交错**（A/B/C 各起一个进程算一波，跑 3 波） | 单 session 在 batch 64 × 长文本下峰值 RSS 就 **2~3.3 GB**（**激活张量**，不是权重）；7 个 session（`1+2+4`）并存会顶穿本机 32 GB ⇒ 换页会**均匀拖慢所有档位**，档位间比较失去意义 |

### 8.11 增量构建：NFR-03 ② 实测（V2 Step 6 / S6-07 / T7-11）

**复现**：`./scripts/eval_incremental.sh`（release；`data/t2-corpus.jsonl` 前 12,000 篇）
**口径**：`helix build --single-chunk --vectors` ⇒ **1 篇 == 1 chunk**，与 §8.2 的 NFR-03 ① 对齐，便于横比。
三个计时在**同一次运行内**取得（跨时段数字不可相减）；追加走**默认原地覆盖**（`--output` 缺省），
`delta` 取语料**尾部** 1200 篇、与 `base` **不相交**（评审 F1 的硬约束：若相交则 1200 条全部命中
查重短路 ⇒ 判据必然通过却什么都没测到）。

| 项 | 实测 | 分解 |
| --- | --- | --- |
| `T_base`（10,800 篇，仅前置，**不计入判据**） | 201.619 s | embed 187.96 s |
| **`T_full`（12,000 篇全量，判据分母）** | **233.107 s** | embed 217.35 s / save 0.122 s |
| **`T_inc`（追加 1,200 篇，判据分子）** | **23.705 s** | load 0.151 s / **embed 21.412 s** / save 0.114 s |
| 预算 `T_full × 10% × 1.2` | 27.973 s | —— |
| **判定** | **23.705 s < 27.973 s ⇒ ✅ PASS** | 余量 4.27 s（**15.3%**） |

**⚠️ 两种时钟，别混用**：三个 `T_*` 是**脚本墙钟**（`run_timed`，含进程启动 ≈0.15 s），
分解项是**进程内读数**（CLI 打印的 `embed` / `加载快照耗时` / `快照已写入`）。
同一进程两者的差即启动开销：追加那趟 `总耗时 23.552 s`（进程内）vs `T_inc 23.705 s`（墙钟）⇒ **≈0.15 s**。
判据一律用墙钟（更保守），**跨项相减时必须在同一把尺子内**。

- 三档 embed 吞吐一致（`T_base` 57.5 条/s、`T_full` 55.2 条/s、`T_inc` 56.0 条/s）⇒
  「只 embed 新增」这一步是**干净的按量计费**，没有隐含的全量回灌
  （若回灌，`T_inc` 会退化到 ≈200 s 量级）。
- `incr.log` 的「**新增 1200 / 去重跳过 0**」是**评审 F1 的直接物证**：delta 与 base
  不相交 ⇒ 这 1,200 条真的走了完整摄入路径，不是被查重短路掉的。
- **`T_inc` 扣掉三段可解释成本后还剩 ≈1.88 s**（**进程内口径**：`总耗时 23.552 s`
  − load 0.151 − embed 21.412 − save 0.114）= 分块 / 倒排 / HNSW 插入 1,200 点的成本。
  （若改用墙钟 23.705 s 则为 ≈2.03 s，差额即上述 ≈0.15 s 启动开销。）
  与 `T_base` 的「纯索引构建」按篇折算（**同样进程内口径**：`201.427 − 187.965 = 13.46 s`
  / 10,800 篇 ⇒ 1,200 篇 ≈ **1.50 s**）**量级吻合**。
- 余量 15.3% 与设计附录 B 的预判（「预期 ≈23 s、阈值 27.1 s ⇒ **通过但不宽裕**」）**高度一致**：
  实测 23.705 s vs 预估 ≈23 s。

**⚠️ 不要把"余量只有 15.3%"误读成"增量收益小"**：增量省下的是 embed 那一段
（217.35 s → 21.41 s，**省 90.2%**，因为 12,000 篇里只有 delta 的 1,200 篇（10%）需要
重新 embed，base 的 10,800 篇（90%）向量已在快照里、不重算）。
但 NFR-03 ② 的分母**已经按 10% 缩过**、只留 1.2× 余量 ⇒ 「省 90%」在数字上就表现为
「实际只用了全量的 **10.17%**，容许 12%」。真正的差别要相对 ① 的口径看（225.5~233 s 量级）。

**图 sidecar 跟随（S6-T13 的实测侧证）**：`base` 的图 sidecar = 10,800 点 / 28.4 MB
（graph 7.1 + data 21.3；快照 47.6 MB，磁盘增量 1.6×）。追加后由 `save()` 的既有链路
**自动重发 manifest**（Step 4 踩过的坑：漏发 ⇒ 新图永远匹配不上、每次冷启动白重建 ≈10 s）；

① 快照**重建**（`hnsw_rs` 建图走 `StdRng::from_os_rng()`、**无 seed** ⇒ 图拓扑不同）；
② **跨时段**（项目既有纪律：跨时段数字不可相减）。**可靠的是比值**：三模式 `QPS(4)/QPS(1)`
从 3.07 / 1.62 / 1.88 变为 2.98 / 1.63 / 1.88 —— 变化 ≤ 3%，与「瓶颈在结构上、不在数值上」一致，
**结论不变**。

#### 结论：×2.5 对**非编码路径**达标，对**含查询编码的路径结构性达不到**

- `bm25` **2.98×**（t=8 到 4.46×，仍在近线性增长）—— 与「索引读路径**零**共享可变状态
  ⇒ 近线性是强先验」**一致**。
- `vector`：**t=4→8 仅 +2.1%**（489.0 → 499.3），**饱和**。
- `hybrid`：**t=4→8 +11.6%**（412.3 → 460.2），**未饱和**，但离 N× 仍很远（1.63× ≪ 2.5×）。
- ⚠️ 两者**不能合并成一句「完全饱和」**（PR #44 评审 P3-3：上一版把 vector 的数字 356.3→353.1
  配给了「完全饱和」这个结论、还写成「+1.0×」，属数字归属与符号错误）。
- 每线程 P50 随 N 近线性增长（`t=8 ÷ t=1`：vector **4.38×**、hybrid **4.51×**，而 bm25 仅 1.77×）
  —— **饱和 + 排队式延迟增长 = 存在某个被串行化的资源**。

#### 根因：查询侧编码被单 session 互斥串行化（**vector 与 hybrid 均已实测**）

代码位置：`embed/local.rs:33-37` 的 `LocalEmbedder { inner: Mutex<TextEmbedding> }`，
`embed_query`（`:73-79`）在**每次查询**上 `lock()`
⇒ **查询侧编码被全局串行化**（fastembed 的 `embed` 需 `&mut self`，故用 `Mutex` 包裹）。

**决定性对照实验（一）—— vector**（⚠️ 协议如实标注：档位 `1,4,8` ｜ `--reps 10` ｜
与上面的基线**不是同一次运行**。做法：把 `embed_query` 临时改成**不加锁**返回常量向量，
**只看吞吐、不看正确性**；实验后已还原并复验）：

| 档位 | 基线（带锁）QPS | **无锁变异** QPS | 基线加速比 | **无锁加速比** |
| --- | --- | --- | --- | --- |
| 1 | 189.2 | 819.3 | 1.00× | 1.00× |
| 4 | 356.3 | **2580.8** | 1.88× | **3.15×** |
| 8 | 353.1 | **3560.9** | 1.87× | **4.35×** |

⇒ 仅移除那一把锁，`--threads 4` 的加速比从 **1.88× 跳到 3.15×**、`--threads 8` 从 1.87× 到 4.35×
且**不再饱和**。⚠️ 上表是**上界**：变异同时移除了 ONNX 推理本身（那一次 t=1 的 QPS 由 189 涨到 819，
正是单次推理被整段替换掉的后果；该处的「单次推理 ≈3.4 ms」是两次不同 `--reps` 运行之差，
**仅供量级参考，不要当独立读数引用** —— PR #44 评审 P3-10）。

**决定性对照实验（二）—— hybrid**（**S6-10 补跑**，收 PR #44 评审 **P2-2** 的遗留；
与实验（一）**同协议、同快照**，并加**同期控制组**归一漂移）：数据与协议见 **§8.13**。
⇒ 结论：**hybrid 的并发瓶颈同样是那把锁**（移除后 t=4 从 **1.73× → 2.51×**、t=8 从 1.79× → 3.87×）
—— **不再是类比推断**。⚠️ 但 hybrid 去锁后仍**低于** vector（2.51× vs 3.15×），与「hybrid 每次检索
多走 `rayon::join` 双 lane 并行（`crates/core/src/query/searcher.rs:207`）、N 个 bench worker 共享同一
全局 rayon 池」这条**本报告未拆分的额外并发维度**一致 —— 即那把锁是**主因**、但不是**唯一**原因。

**量级自洽**（由 N=1 与 N=4 反解「串行分量 e / 并行分量 s」，`QPS(N) = N/(N·e+s)`）：

| mode | e | 理论上限 `1/e` | 实测 t=4~8 | 达上限 |
| --- | --- | --- | --- | --- |
| bm25 | **0.159 ms** | 6300 QPS | 2147~3215 | 34~51%（仍在爬） |
| vector | **1.445 ms** | 692 QPS | 489~499 | **71~72%（已贴顶）** |
| hybrid | **1.913 ms** | 523 QPS | 412~460 | 79~88% |

（PR #44 评审 P3-2：上一版此处给 hybrid `e ≈ 2.3 ms / 433 QPS`，与表内数字**不自洽**
—— 按同一公式重算应为 `2.51 ms / 398`。本版全部重算，每个数字都可由表内 N=1 与 N=4 复现。）

#### 影响与必须澄清的一处**定义面措辞**

- ⚠️ `requirements-spec.md` NFR-10 的备注里写「读路径**零**共享可变状态 ⇒ 近线性是强先验」——
  这句对**索引读路径**成立（bm25 2.98× 即证据），但**端到端**的 vector/hybrid 查询还包含
  **查询侧编码**，那条路径**有**共享可变状态（上述 `Mutex`）。判据的原始前提对这两种模式不成立。
- 判据原文（`requirements-spec.md:374`）为 `--threads 4 QPS ≥ --threads 1 × 2.5`，**并未**写明
  「三模式都要满足」。本报告的「未达标」用的是**最保守读法（三模式全过）**；按最宽松读法
  （任一路径达标）则为达标。**取哪种读法属定义面决策**（PR #44 评审对措辞的修正）。
- ✅ **裁定（S6-10，2026-09-13，已回写需求侧 v1.15）**：采用 **「收窄 ② + 保持 NFR-10 打开」**——
  ① 判据 ② 的**适用范围收窄**为「**不含查询侧编码的读路径**」（bm25 2.98× 在该范围内**达标**）；
  ② 另立 **③ 编码侧并发**条目，**明记含查询侧编码的端到端路径（vector 1.88× / hybrid 1.63×）
  当前不达标**，**NFR-10 整体保持「打开」、不关闭**；③ **复审触发条件** = 「查询侧会话池
  （每 worker 独立 session）落地时」，届时须**先答挂起的 Q3**（不同 `sessions` / `intra_threads`
  是否改变向量数值 —— 若改变会破坏 S6-T11 的逐位一致前置条件）。
  这满足复审 §六 的要求（**同时**写明「保持打开」与「复审触发条件」），避免 D-S6-08 已否决的
  「只记录不判定」。**本轮不动生产代码**（纯文档 + 风险登记）。
- ⚠️ **不得把 ② 的收窄读成「判据被削弱」**：收窄的是**适用范围**（标定对象），不是阈值（仍为 ×2.5），
  且 ③ **显式留痕**了被排除的那两条路径的实测失败 —— 收窄是「把判据钉在它能成立的对象上」，
  不是「把不达标的部分藏起来」。
- **T7-09 的「不投」不能直接外推到这里**：T7-09 测的是**建库路径的多 session**（batch 64 已让
  session 饱和 ⇒ 收益仅 +11.7%/+16.0%，而 RSS +96.4%）；**查询路径每次只编 1 条**，
  session 利用率低得多 ⇒ 同样的池化在**查询侧**的收益上界远大于建库侧。这是**新证据**，
  不改变 T7-09 的结论，但意味着「池化」在查询侧需要**单独评估**（含 RSS 代价）。
- ✅ **已登记风险 R43**（2026-09-13，S6-10；`architecture-design.md` §14.4）= **查询侧编码把并发读
  吞吐封顶**（`embed/local.rs:35` 的 `Mutex<TextEmbedding>` ⇒ `embed_query`（`:73-79`）每次查询
  `lock()`）。对照实验见 §8.13。

#### 局限

1. **单机单次**（10 核 / AC / 非 CI）；加速比是**相对首档**的内部比值，**不是**跨机可引用指标。
2. **不得与 NFR-02 横比**：并发下 per-query 延迟含排队（本次 t=8 的 vector P99 已到 21.5 ms）。
3. 无锁变异实验**只验吞吐、不验正确性**（常量向量使结果无意义 —— hybrid 变异组的效果指标实测掉到
   NDCG **0.0021**，正是该效应的直接读数；见 §8.13）；它的作用是**归因**，不是「建议这么改」。
   **覆盖范围**：vector 见上表、**hybrid 见 §8.13**（S6-10 补跑，收评审 P2-2 遗留）。
4. 残余非线性：即使无锁，t=4 也仅 **3.15×（vector）/ 2.51×（hybrid）**、t=8 仅 **4.35× / 3.87×**（均 < N）
   ⇒ 检索路径本身还有（较小的）非并行成分，未进一步拆分；hybrid 那一份更大，与它的
   `rayon::join` 双 lane 共享全局池（§8.13）一致。
5. **跨快照 / 跨时段不可比**：`hnsw_rs` 建图无 seed ⇒ 每次重建的图拓扑不同；
   本节的绝对值只描述**本次**快照。

### 8.13 hybrid 无锁对照实验：R43 的 hybrid 归因由「推断」升为「实测」（V2 Step 6 / S6-10）

**背景**：§8.12 的「根因」小节把 hybrid 的并发瓶颈也归因到 `embed_query` 的那把 `Mutex` ——
但当时**只有 vector 的对照**，hybrid 那一句是**类比推断**（PR #44 评审 **P2-2** 指出）。
本节补跑 hybrid 的对照，把 R43 的 hybrid 分支闭合。

**协议**（与 §8.12 的 vector 对照同口径，**并加同期控制组**）：
- **变异** = 把 `embed_query` 整体移出被测路径（`let _ = text; Ok(vec![0.5_f32; self.dim])`）
  —— **不加锁、也不做 ONNX 推理**；**只看吞吐、不看正确性**；实验后已还原并复验（源码 md5 前后一致）。
- **三组同机同期**：控制组 A（现码）→ 变异组 B（重建 release）→ **还原** → 控制组 A'（归一漂移）。
  这是与 §8.12 vector 对照的**唯一协议差别**（vector 那次没跑同期控制组）。
- **快照** = 与 PR #44 权威运行**同一份** 12K（`/tmp/helix-threads2/base.snapshot`）；
  命令 = `helix bench --modes hybrid --threads 1,4,8 --reps 20 --k 10`；档位**含判据点 t=4**。

**数据**（`/tmp/helix-hybrid-ctl/{base,mut,base2}.json`；表内 QPS 为各 worker 计时窗内口径）：

| 组 | t=1 | t=4 | t=8 | **QPS(4)/QPS(1)** | QPS(8)/QPS(1) | NFR-10（≥2.5） |
| --- | --- | --- | --- | --- | --- | --- |
| 控制组 A（现码） | 207.4 | 358.1 | 371.8 | **1.73×** | 1.79× | ❌ fail |
| **变异组 B（无锁）** | 932.8 | 2344.9 | 3607.8 | **2.51×** | 3.87× | ✅ pass（**边际**，余量 **0.6%**） |
| 控制组 A'（现码；还原后） | 222.4 | 336.7 | 384.7 | **1.51×** | 1.73× | ❌ fail |

**同期控制组给出的漂移界**：A → A' 的 `QPS(4)/QPS(1)` 由 1.73× 变到 1.51×（相对 **−12.3%**）、
`QPS(8)/QPS(1)` 由 1.79× 到 1.73×（−3.5%）⇒ **漂移量级 ~12%**。而变异组相对两组控制组的抬升是
**+45.6%（vs A）/ +66.0%（vs A'）**，**远大于漂移** ⇒ **结论不由漂移解释**。

**结论（三条）**：

1. **hybrid 的并发瓶颈同样是那把锁** —— 移除它，`QPS(4)/QPS(1)` 从 1.5~1.7× 抬到 **2.51×**、
   `QPS(8)/QPS(1)` 从 1.7~1.8× 抬到 **3.87×**。**§8.12 的类比推断至此成为测量**。
2. ⚠️ **但去锁后 hybrid 仍低于 vector**（t=4 **2.51× vs 3.15×**、t=8 3.87× vs 4.35×），且 t=4
   只**刚好**越过门槛（余量 **0.6%**，**在 ~12% 的漂移面前属边际**）⇒ 那把锁是**主因、不是唯一**。
   与「hybrid 每次检索多走 `rayon::join` 双 lane 并行（`crates/core/src/query/searcher.rs:207`）、
   N 个 worker 共享同一**全局 rayon 池**」这条本报告**未拆分**的额外并发维度一致。
3. 变异组 `t=1` 的 per-thread P50 从 **4.22~4.54 ms** 掉到 **1.05 ms**（≈ **−77%**）—— 这是「变异把
   ONNX 推理**本身**也一并移除」的直接体现（同 §8.12 的保留意见）⇒ **本节的数字是上界**：
   它只回答「**锁是不是瓶颈**」，**不能**读成「修好这把锁就能拿到 2.51×」（真实修法是**会话池**，
   每 worker 仍要跑编码）。

**局限（本节新增项；其余与 §8.12 共享）**：

- 变异组的效果指标 NDCG 实测 **0.0021**（基线 0.5200）⇒ **变异确实生效**，不是「注入了但没编进去」的
  假阴性。这是本次相对 §8.12 vector 对照**多做的一步自证**。
- `hits_signature` 在三个档位下相同（各组 `sigs.len() == 1`）—— 对变异组是**平凡成立**（常量向量），
  **不构成**对变异组的正确性论证（变异组本就不看正确性）。
- 仍受「**单机单次**（10 核 / AC / 非 CI）」与「`hnsw_rs` 建图无 seed ⇒ 跨快照不可比」两条既有纪律约束。

## 9. 数据诚信声明

**已知偏差**：
1. **随机负例的潜在假负例**：负例按哈希秩均匀抽样，未标注的段落可能含相关段落（假负例）。
2. **分桶为启发式代理**：o* 词汇重合度不是人工判类，exact/paraphrase 边界存在误分。
3. **人类搜索 query 作为 Agent query 的代理**：T2Ranking 是网络搜索日志，非 LLM 生成 query（query 分布、噪声形态与 Agent 场景有差异，见项目立论五差异）。
4. **12K 子集难度低于 230 万全库**：BM25 MRR@10=0.6394（子集）vs 论文全库 0.359，绝对指标不可与论文基线直接对比，仅量级对照。

**结论适用范围**：结论仅对「T2Ranking 中文网络语料 + bge-small-zh-v1.5 + 12K 段落」成立，
不外推到其他域、规模或查询分布。

**未达预期项的如实记录**：
- **hybrid NDCG 未超越 vector 单路**（0.5183 vs 0.5249，p=0.385 不显著）：RRF 融合在
  paraphrase 桶被弱路 BM25 稀释（3.3 节）。但 hybrid 在 MRR@10(1) 与 Recall@10(1) 两项
  对 Agent 场景更关键的指标上全场最高，且 exact/natural/mixed 桶显著优于 BM25 单路。
  融合的价值在「首条精确率」而非「NDCG 整体」——这与项目质量属性优先级（MRR > Recall > NDCG）一致。
- **预期占优假设（9.4）在 exact 桶被推翻**：exact 桶 hybrid 最优而非 BM25（3.3 节）。
- ~~**NFR-04 冷启动未达标**：HNSW 图重建 11.57s > 2s 目标（P4 已知风险 D7）~~ → **已解决**（2026-09-06，V2 Step 2 / ADR-A）：完整冷启动 ≈100ms，达标。代价是磁盘 1.6×，且达标依赖图 sidecar 命中（降级路径仍 ~10s，故配 NFR-07 降级可观测）。
