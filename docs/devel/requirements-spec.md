## 2. 项目背景与目标

### 2.1 背景与问题陈述

Agent 应用（RAG 知识库、长期记忆、代码助手）的核心瓶颈往往不在大模型本身，而在**检索**：召回错了，后面生成得再好也是幻觉。

市面上现成的检索方案（Elasticsearch、Milvus、各类向量库）各有定位，但它们要么是给人用的搜索引擎，要么是纯向量数据库，**缺少一层专门针对 Agent 作为调用方而设计的内核**。这个缺口不是功能缺口，而是接口与质量属性层面的缺口——具体差异见第 4 章。

### 2.2 项目目标

| 目标 | 说明                                               |
| -- | ------------------------------------------------ |
| G1 | 实现 BM25 关键词检索与向量语义检索双路召回，并完成融合                   |
| G2 | 内核全部抽象为 trait，分词器 / 嵌入模型 / 向量索引 / 融合策略 / 精排器均可替换 |
| G3 | 接口设计上充分照顾 Agent 调用方的特殊性（见第 4 章）                  |
| G4 | 单机万级文档下跑通全链路，效果与延迟可量化                            |
| G5 | 架构为后续扩展（Rerank、增量、分布式）留出明确位置                     |

### 2.3 项目定位与边界

**一句话定位**：通用检索引擎内核，不做场景假设，场景层（知识库 RAG / Agent 记忆 / 代码检索）后续接入。

由此产生的边界划分：

- ✅ 内核负责：结构化输出、可解释性、防空召回、低延迟、幂等写入、元数据过滤
- ❌ 内核不负责：知识库的 schema、记忆的时序衰减公式、代码检索的符号关系

> 这条边界是硬约束。内核一旦内置领域逻辑，场景层就只能"将就"，最终退化为又一个专用引擎。

### 2.4 成功标准

- [ ] 在示例中文语料上，混合检索的 Recall@10 与 MRR@10 **优于** 单独的 BM25 与单独的向量检索
- [ ] 单次混合检索 P99 延迟（不含模型冷启动）< 20ms @ 1 万 chunk
- [ ] 索引快照加载时间 < 2s，显著优于重建索引
- [ ] 全部核心 trait 均有 ≥2 个实现或明确的替换路径

## 3. 术语与缩略语

> 本文档是术语的**唯一定义来源**，架构文档直接使用，不重复定义。

| 术语            | 含义                                          |
| ------------- | ------------------------------------------- |
| Document      | 摄入的原始文档，一个文档可切分为多个 Chunk                    |
| Chunk         | 检索与返回的最小单位，通常 200~500 字                     |
| Term          | 分词后归一化得到的索引词                                |
| Posting       | 倒排表中一条记录：`(chunk_id, term_freq, positions)` |
| 倒排索引          | Term → Posting 列表 的映射                       |
| 正排存储          | ChunkId → 原文、元数据 的映射                        |
| df            | document frequency，包含某 Term 的 Chunk 数量      |
| avgdl         | 平均 Chunk 长度（以 Term 数计）                      |
| 召回（Retrieval） | 从全量中快速找出候选集，重速度                             |
| 精排（Rerank）    | 对候选集精细打分重排，重精度                              |
| 融合（Fusion）    | 把多路召回结果合并为统一排序                              |
| RRF           | Reciprocal Rank Fusion，倒数排名融合               |
| Lane          | 一路独立的召回通道（如 BM25 lane、向量 lane）              |

## 4. 调用方特征分析：Agent 场景的特殊性

> 本章是全部需求的来源。**如果这个引擎和 Elasticsearch 没有区别，那它就不该存在。**

### 4.1 前提性张力：通用内核 vs Agent 场景

"通用内核"与"Agent 场景"之间存在张力：通用意味着不做场景假设，Agent 场景意味着要为 Agent 做优化。

本项目的解法是：**把 Agent 场景的特殊性翻译为「接口约束」与「质量属性约束」，而不是翻译为「领域逻辑」。**

- ✅ 翻译成接口约束：结构化输出、可解释性、防空召回、低延迟、幂等写入、元数据过滤
- ❌ 不翻译成领域逻辑：不内置知识库 schema、不内置记忆衰减公式、不内置符号关系

这样场景层（知识库 / 记忆 / 代码）才能真正接进来，而不是被内核的假设绑死。

### 4.2 变化一：查询的发出方从人类变成 LLM

|    | 人类查询                   | Agent 查询                                  |
| -- | ---------------------- | ----------------------------------------- |
| 形态 | 短、关键词化（"rust bm25 实现"） | 完整自然语言问句（"在 Rust 里怎么实现一个支持中文的 BM25 检索？"）  |
| 长度 | 2~5 词                  | 10~40 词，含大量虚词                             |
| 质量 | 意图明确                   | 可能含**指代**（"它的默认值是多少"）、可能含**幻觉词**（模型编造的术语） |

**工程后果**

- 长 query 直接喂 BM25，虚词会稀释信号
- 含幻觉词时该词 `df = 0`。若用 AND 语义 → **整体零召回**，这是 Agent 场景最典型的翻车方式
- 含指代时，语义向量会漂移，向量路也可能失效

**设计应对**

- FR-04：BM25 **默认 OR 语义**，禁止 AND。单个 term 未命中只损失该 term 的贡献，不影响整体
- FR-13：空结果必须携带 `EmptyReason`（是库里没文档？还是词全没命中？还是被过滤掉了？），让 Agent 能据此决定"改写 query / 换数据源 / 直接回答"
- FR-21：支持多 query 输入后融合，为后续的 HyDE、multi-query 改写留出接口（内核不做改写，只做承载）

### 4.3 变化二：检索结果是 LLM 的输入，不是给人看的列表

人可以翻页、扫标题、自行判断 relevance；Agent 是 Top-K 直接进 prompt，**一次机会，没有翻页这个交互**。

**工程后果**

- **前几条的精确率** 比 "有没有涵盖全部相关文档" 更关键
- **重复内容极度有害**：同一句话出现在 3 个 chunk 里 → 浪费 3 倍 token，且污染上下文、干扰注意力
- 结果必须**可溯源**，否则 Agent 无法标注引用，用户无法验证

**设计应对**

- FR-12：`Hit` 必须携带 `doc_id / source / char_start / char_end / metadata`，并提供 `to_context_block()` 直接产出可拼进 prompt 的文本块
- FR-24（v2）：结果去重，MMR 或同文档相邻 chunk 合并
- FR-25（v2）：按 token budget 裁剪，防止撑爆上下文窗口

### 4.4 变化三：检索位于 Agent 循环的关键路径，且被高频调用

一次用户提问，Agent 可能跑 5~20 轮，每轮调 1~3 次检索 → **单次会话几十次调用**。

人类搜索等 200ms 无感；Agent 场景下 50 次 × 100ms = 5s，直接体现在端到端延迟上，用户能明确感知。

**工程后果**

- **P99 比均值重要**。查询路径上不允许有隐藏的 O(n) 扫描或磁盘 IO
- Embedding 是最大延迟源：本地 bge-small 单条约 5~15ms，远程 API 则 50~200ms

**设计应对**

- NFR-02 明确延迟上限；两路召回并行执行、全内存索引、查询路径零磁盘 IO
- FR-20：query embedding 缓存（Agent 多轮循环中大量 query 是重复的）
- NFR-07：内核暴露 `SearchResponse.took`，让上层能观测与告警

### 4.5 变化四：Agent 需要能"自查"检索质量

人看到结果不对会自己改 query。Agent 需要**信号**来判断"这次召回靠谱吗"，才能决定是改写 query、换工具、还是直接回答。

**一个高价值的诊断信号**：BM25 命中但向量路未命中，通常意味着"词汇匹配但语义不相关"（如 query 里出现的词恰好是文档里的高频噪音词）；反之，向量路命中但 BM25 零命中，意味着"语义相关但用词完全不同"。

**设计应对**

- FR-13：每条 `Hit` 携带 `Explain`，包含各 lane 的 rank 与 score、`matched_terms`、融合分
- 上层可据此构造策略：两路都命中 → 高置信；仅一路命中 → 降低置信或触发重试

### 4.6 变化五：写入模式不同

传统搜索系统的索引由离线管道批量构建。Agent 场景下，Agent 自己会往里写（新记忆、新经验、刚抓取的网页），写入是**零散、持续、与主流程异步**的。

**工程后果**

- 必须幂等（同一个文档反复灌入不能产生重复结果）
- 增量写入不能阻塞读

**设计应对**

- FR-15：doc 级 upsert，按 `content_hash` 或 `source` 去重
- FR-17：主索引 + delta 区，delta 异步合并，读不阻塞

### 4.7 约束推导汇总

| Agent 场景特征           | 对内核的要求             | 落到需求          |
| -------------------- | ------------------ | ------------- |
| query 由 LLM 生成，质量不稳定 | OR 语义、防空召回、显式空原因   | FR-04 / FR-13 |
| 结果直接进 prompt，无翻页     | 结构化 + 可溯源 + 去重     | FR-12 / FR-24 |
| 高频调用，关键路径            | 低 P99、并行、缓存、零 IO   | NFR-02 / FR-20 |
| 需要自查检索质量             | 可解释性、双路命中信号        | FR-13         |
| Agent 自己写入           | 幂等 upsert、非阻塞增量    | FR-15 / FR-17 |
| 多场景共享内核              | 全 trait 抽象，不内置领域逻辑 | G2 / 2.3 节    |
| 需要按 scope 限定范围       | 元数据过滤              | FR-14         |

### 5.3 关键需求详细规约

以下 6 条是本项目的差异化需求，单列规约以避免实现时被简化掉。

#### 5.3.1 FR-04：BM25 强制 OR 语义

| 项    | 规约                                                       |
| ---- | -------------------------------------------------------- |
| 行为   | query 中多个 term 之间为 OR。未命中的 term 贡献 0 分，其余 term 正常累加      |
| 禁止   | 第一版不提供 AND / 布尔查询语法                                      |
| 理由   | Agent 的 query 由 LLM 生成，可能含幻觉词。AND 语义下单个 term 的 `df=0` 会导致整体零召回，且**没有任何错误提示**，是最隐蔽的失败模式 |
| 验收   | 构造含 1 个不存在词的 query，检索仍需返回其余 term 的命中结果，且 `Explain.matched_terms` 中不含该词 |

#### 5.3.2 FR-12：结构化结果返回

| 项    | 规约                                                                            |
| ---- | ----------------------------------------------------------------------------- |
| 必带字段 | `chunk_id`、`doc_id`、`score`、`text`、`source`、`metadata`、`explain`              |
| 溯源字段 | `source`（文件路径/URL/标题）、`char_start`、`char_end`（原文字符偏移）                          |
| 上下文块 | 提供 `to_context_block()`，直接产出带出处标注、可拼进 prompt 的文本                               |
| 理由   | Agent 无法翻页，且必须能标注引用供用户验证                                                       |
| 验收   | 任一条 `Hit` 能反查回原文，偏移量精确；`to_context_block()` 输出含 source 标注                       |

#### 5.3.3 FR-13：检索可解释性与空结果原因

| 项      | 规约                                                                                 |
| ------ | ---------------------------------------------------------------------------------- |
| `Explain` | 每条 Hit 携带：`matched_terms`、各 lane 的 `score` 与 `rank`、`fused_score`                   |
| `EmptyReason` | 空结果时必须给出原因，取值：`NoDocuments`（索引为空）/ `AllTermsUnmatched`（词全部未命中，提示 query 可能含幻觉词）/ `FilteredOut`（有候选但被 filter 全部过滤，提示放宽 scope） |
| 诊断价值   | 上层可据此构造策略：两路都命中 → 高置信；仅一路命中 → 降低置信或触发重试                                            |
| 验收     | 三种空结果场景各能返回对应 `EmptyReason`；`--explain` 模式下每条结果的分 lane rank/score 完整可查              |

#### 5.3.4 FR-15：幂等 upsert 与删除

| 项    | 规约                                             |
| ---- | ---------------------------------------------- |
| 去重键  | `content_hash`（默认）或 `source`，二选一可配置            |
| 语义   | 同一文档重复 upsert 不产生重复 chunk；upsert 已存在文档时先删后插    |
| 删除   | 墓碑标记，异步物理清理；删除后统计量须与全量重建一致（V2 扩展：向量侧软删除 + 存活过滤，见 FR-26） |
| 理由   | Agent 会反复灌入同一份内容（重新抓取的网页、重复记忆）                 |
| 验收   | 同一文档 upsert 两次，chunk 数不翻倍，检索结果不变；删除后统计量无漂移     |

#### 5.3.5 FR-17：增量写入不可阻塞读

> 交付状态：V1 已交付「主索引增量写入」；「读不阻塞写」的 delta 分段完整版归 V2.1（`plan-v2.md` Step 7）。

| 项    | 规约                                                           |
| ---- | ------------------------------------------------------------ |
| 行为   | 新增文档进入 delta 区，立即对检索可见；delta 在后台异步合并进主索引                     |
| 禁止   | 合并期间不得阻塞读请求；不得以"重建索引中"为由拒绝查询                                 |
| 理由   | Agent 写入是零散、持续、与主流程异步的，任何阻塞都会直接卡住 Agent 循环                   |
| 验收   | 写入后立即可查；合并过程中持续发起检索，无失败、无超时（延迟变化须在 NFR-02 范围内）                |

#### 5.3.6 FR-18：Reranker 接入

| 项    | 规约                                                  |
| ---- | --------------------------------------------------- |
| 交付（V1） | 定义 `Reranker` trait + `NoOpReranker` 实现，接入查询流程但不改变排序 |
| 交付（V2.0） | 接入 `bge-reranker-v2-m3`（fastembed `TextRerank`），候选窗口从 `take(k)` 放开到 `candidate_k`/可配 R |
| 理由   | V1 保证查询链路中已有精排位置；V2.0 落地真实精排以提升首条精确率（MRR） |
| 验收   | `NoOpReranker` 与移除精排环节结果一致（V1）；接入后 hybrid MRR@10(1) 相对基线可测提升，精排延迟满足 NFR-12（V2.0） |

### 6.3 质量属性优先级

当质量属性冲突时，按以下顺序取舍：

| 序 | 质量属性        | 取舍说明                                     |
| - | ----------- | ---------------------------------------- |
| 1 | **正确性 / 确定性** | 结果不对比慢更糟；同输入必须同输出，否则无法调试与回归              |
| 2 | **首条精确率（MRR）** | Agent 无翻页，第一条错了后面全白搭；优先于召回率              |
| 3 | **延迟 P99**  | 在 NFR-02 上限内越高越好，但超出上限即视为不达标             |
| 4 | **召回率（Recall）** | 重要，但低于前三者                                |
| 5 | **资源占用 / 索引体积** | 最后考虑，MVP 阶段不为体积牺牲正确性                     |

## 7. 明确不做（Out of Scope）

以下内容**第一版明确不做**，避免范围蔓延：

| 不做                                  | 原因                         |
| ----------------------------------- | -------------------------- |
| 分布式 / 分片 / 副本                       | 单机 MVP 优先，架构留位             |
| HTTP / gRPC 服务层                     | 先以库 + CLI 形态交付             |
| PDF / Word / HTML 文档解析              | 属于摄入层，非检索内核职责              |
| 查询改写 / HyDE / 多轮对话管理                | Agent 应用层职责，内核只留多 query 接口 |
| 权限 / 多租户隔离（鉴权、租户边界、访问控制）             | 范围外——内核只提供命名空间过滤机制（FR-32），鉴权/策略归场景层 |
| 图检索 / 关系推理                          | 不在本期范围                     |
| posting 压缩（varint / roaring bitmap） | MVP 用朴素 `Vec<u32>`，P4 优化项  |
| 查询语法（布尔、短语、通配符）                     | MVP 只用 OR 语义，位置信息先存好备用     |

## 9. 验收与评测要求

### 9.1 验收方式

| 层级    | 内容                            | 对应架构文档章节    |
| ----- | ----------------------------- | ----------- |
| 单元测试  | 算法正确性、接口一致性、统计量维护；**含与 `tantivy` 的 BM25 排序对照** | 架构文档 12.1、ADR-007 |
| 集成测试  | 端到端链路（摄入 → 提交 → 快照 → 加载 → 检索） | 架构文档 12.2   |
| 效果评测  | 本章 9.2 ~ 9.5，在 P5 阶段执行         | `helix bench` |
| 依赖合规  | 全部依赖在 License 白名单内（NFR-09）     | 架构文档 ADR-008；`make deny` |

### 9.2 评测指标定义

| 指标           | 定义            | 用途                         |
| ------------ | ------------- | -------------------------- |
| Recall@10    | 前 10 条中相关文档占比（相关性 ≥ 阈值计为相关，阈值可调） | 衡量召回能力                     |
| MRR@10       | 首个相关文档排名倒数的均值（阈值同上） | 衡量"第一条对不对"，**Agent 场景更重要** |
| NDCG@10      | 折损累积增益（**分级增益 gain = 2^rel − 1**，rel ∈ 0~3） | 综合排序质量                     |
| P50 / P99 延迟 | 端到端检索耗时       | NFR-02 / NFR-03 验证          |

> 相关性等级来自 T2Ranking 的 4 级专业标注（见 9.4）。分级 NDCG 用完整等级信息；Recall / MRR 阈值化以兼容二元口径，阈值经 `helix bench --rel-threshold` 可调。

### 9.3 强制对照实验

**必须做，否则无法证明混合检索的价值。**

| 配置           | 预期                        |
| ------------ | ------------------------- |
| BM25 only    | 术语查询好，改写查询差               |
| Vector only  | 改写查询好，术语查询差               |
| Hybrid (RRF) | **两类查询都不差，整体最优** ← 需被数据证实 |

### 9.4 评测数据集要求

**数据源**：开源数据集 **T2Ranking**（清华 THUIR，SIGIR 2023；License **Apache-2.0**；HuggingFace 直接下载无注册墙）。选择依据：真实中文搜索查询 + 真实网页段落、4 级专业相关性标注（每对 ≥3 人多数票）——**彻底消除"实现者自写语料、自标注"的偏差**。候选对比（DuReader-retrieval / mMARCO-zh / Multi-CPR）与选型过程见 `p5-design.md` 第 3 章。

**装配要求**：经转换器 `t2_prep.rs`（**固定种子，可复现**）从 dev 集装配两份产物：

| 产物                      | 规模                | 要求                                                         |
| ----------------------- | ----------------- | ---------------------------------------------------------- |
| `data/t2-corpus.jsonl`  | ~12K 段落           | qrels 池内段落全集 + 均匀采样负例补足；真实中文网页段落，词频自然分布；规模对齐 NFR"1 万 chunk"口径 |
| `data/t2-queries.jsonl` | ~320 条查询，**四类各 ~80 条** | 词汇重合度启发式分桶（不依赖任何检索器输出）；携带 4 级相关性标注（T2Ranking qrels） |

四类查询与预期占优一路：

| 查询类型                    | 预期占优的一路   |
| ----------------------- | --------- |
| 精确术语匹配                  | BM25      |
| 同义改写                    | 向量        |
| 中英混合术语                  | 混合        |
| 长句自然语言问句（Agent 典型输入）    | 混合        |

**装配诚信约束**：随机负例存在潜在假负例、分桶为启发式近似——两者必须在评测报告中披露（见 9.5）；与 T2Ranking 论文公布的基线数字（如 BM25 MRR@10=0.359）仅作量级对照，不构成可比基准（子集 ≠ 原全集）。

### 9.5 数据诚信要求

**参数调优**：对 `k1 ∈ {1.0, 1.2, 1.5, 2.0}` × `b ∈ {0.3, 0.5, 0.75, 0.9}` 做网格搜索，以 NDCG@10（分级）为目标选优。

> 如调优后混合检索未能优于最优单路，需**如实记录并分析原因**（常见于：子集装配偏差、embedding 模型与语料域不匹配、真实查询与 Agent 生成查询的差异），**不得粉饰数据**。数据集装配的固有局限（随机负例、启发式分桶）必须一并披露。
