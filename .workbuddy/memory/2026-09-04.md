同步在 plan-v2 §4.0 H2 与 Step 1 条目加了指向该设计的交叉引用。

**本次最重要的调研结论（推翻了 plan-v2 的隐含假设）**：hnsw_rs 0.3.4 `search_filter` 不是"免费下推"：
- `DataId = usize`（hnsw.rs:50），insert 传的 chunk_id 可直接用于 `FilterT::hnsw_filter(&usize)`
- 被过滤节点**仍进 candidate_points**（hnsw.rs:1030 push 在 filter 判断之前）→ 连通性不破，能穿过被过滤区
- 被过滤节点不进 return_points 堆；堆上限 ef；**有 filter 时不 fast return**（hnsw.rs:974-993），
  一直扩展直到凑够 ef 个通过点 → 低选择度下退化为整图遍历
- 外层再截断 min(knbn, ef)（hnsw.rs:1537-1557）
⇒ **带 filter 时 ef 语义变了：既是搜索宽度也是目标收集数**。沿用 ef_search=200 会在 0.1% 选择度下全图遍历。
  设计策略：`ef = clamp(k*4, k, 256).min(allowed.max(k))`；低选择度接受召回不足 + Metrics 暴露 shortfall。

设计关键决策（D-S1-01~08）：
- **存活状态只住 Index.forward**（单一真源），检索时以位图谓词传给向量路；**VectorIndex 不加 tombstone**
  （理由：双写必漂移；且快照 load 时 raw_vectors 全量重灌，向量侧状态无法从快照恢复）
- 自研 `Bitmap`（Vec<u64>）不引 roaring：ID 稠密连续，且位运算与迭代序无关 → 天然保 NFR-06（现状 HashSet 无此保证）
- 字段索引 doc 级位图 + 每查询一次 O(N) 展开成 chunk 位图（纯位运算，热路径退化为一次位测试）
- **快照格式不变**（FORMAT_VERSION 仍 2）：存活位图从 chunks 的 Some/None 重建、字段索引从 docs metadata 重建
  → 与 Step 2/3 的 ADR-A（图持久化格式）完全解耦
- `allowed_chunks` 保留为 oracle（等价性测试/bench 对照），移出查询路径
- 顺带发现：`search/index.rs:250-252` 注释「已删向量会被丢弃」**不成立**（raw_vectors 无移除路径，save 原样导出，load 全量重灌）→ 幽灵候选跨快照永续

### ⭐ 最关键的反转：`search_filter` 的停止条件（我 v0.1 判断错了）
逐行复核 `hnsw_rs-0.3.4/src/hnsw.rs`（已精确定位行号，见附录 B）：
- `983-992`：无 filter 时 `return`（984）；**有 filter 时只做 `retain` 剔除未通过过滤的入口点（986-991），不 return，fall-through 继续循环**
  ⇒ **带 filter 的 search_layer 从不 fast return**，唯一正常终止是候选队列耗尽（while 在 960）
- `1019`：`if e_dist_to_p < f_dist_to_p || return_points.len() < ef`
  ⇒ **堆内通过点数 < ef 时距离剪枝全程关闭**，任何邻居都进候选 ⇒ 候选持续膨胀
- ⇒ 判据：**只要 `allowed < ef`，结果堆恒填不满 ⇒ 剪枝永不开启 ⇒ 必然整图遍历**。
  这是**库层结构性行为，调参治不了**（调 ef 只能决定"是否进入整图遍历"，不能降低成本）
- `1519`：`ef = ef_arg.max(knbn)` ⇒ 输出上限恒为 `min(knbn,ef) = knbn`
  ⇒ **`knbn` 才是输出条数旋钮，`ef` 只是搜索宽度**；想多返回要调 knbn 不是 ef

### 由此产生的设计改动
- **D-S1-05 重写为双路径**：
  - path A（无用户过滤，热路径）→ **走普通 `search()` 保留 fast-return**，
    `knbn = min(len, ceil(k/alive_ratio)+k).min(1024)`，`ef` 仍 200，返回后 `retain(alive)` + 稳定排序 + truncate
    （理由：`search_filter` 会禁用 fast-return 改变热路径成本结构；且 v0.1 的 ef=120 < 现状 200 会静默降召回）
  - path B（有用户过滤）→ `search_filter`，`ef = min(max(4k,k), 256)` **纯宽度，删掉 v0.1 无效的 `.min(allowed.max(k))`**
    （评审论证：allowed<ef 时堆恒不满剪枝本就关闭，夹逼无效；allowed≥4k 时该 min 又不生效）
- **D-S1-04 字段索引全类型登记**：`json_to_string`（filter.rs:51-56）对 bool/null/object/array 也返回字符串，
  `matches()` 能匹配但 v0.1 只索引 string/number ⇒ **静默假阴性**。v0.2 全类型进 `terms`，数值额外进 `numbers`。
  ⚠️ 保留反直觉既有行为：`year:2021.0` 用 `Eq("year","2021")` 匹配不上（"2021"≠"2021.0"），字段索引必须原样复刻
- **D-S1-09 惰性谓词（评审未提出，自查发现）**：v0.1 的 `expand_to_chunks` 仍是**每 query O(N) 全扫**，
  只把 O(N) 次 JSON 求值换成 O(N) 次位运算，**O(N) 没消掉**，而 Q-I1 病根正是 O(N)。
  v0.2 改为 `contains(chunk_id) = alive(chunk_id) && doc_bits[doc_of(chunk_id)]`（两次 O(1)），
  每 query 成本降为 **O(匹配文档数)**，与语料规模解耦。需 `ForwardStore` 增 `doc_chunk_count: Vec<u32>` 供 `allowed_count` O(|匹配|) 精确求值
- **D-S1-11 `query_has_hits` 探针**（解 P1-5）：下推后"query 本来有候选"的信号丢失。
  用 `Index::term_id`(mod.rs:237) + `postings_by_id`(:242) 判 query 是否命中词典（postings 删除时已物理摘除 ⇒ 有 postings 即有活候选），
  O(|query 词数|)。判定规则 **query 侧信号优先**：NoDocuments → AllTermsUnmatched → FilteredOut，保持与现状兼容
- **D-S1-10 契约**：`None = 不过滤任何东西（含已软删除）`。直连向量/BM25 路（逃生舱、bench）**不自动获得存活过滤**，
  必须经编排层或显式构造 `AliveOnly` —— 否则"Q-C1 已修复"被绕过而不自知
- **D-S1-12 分层**：`bitmap.rs` / `predicate.rs` 为无依赖叶模块；`vector`、`retriever` 只依赖 `predicate`，
  不 import `query::filter` 或 `index`（避免把 vector→index 拖成文件级耦合）
- **撤回一条伪证**：v0.1 称"HashSet 迭代序威胁 NFR-06"不成立 —— `allowed` 只用于 `retain`（保序），
  lane 顺序由 sort(score→chunk_id) 决定。位图理由改为：内存小、count_ones O(1)、集合运算与迭代序无关
